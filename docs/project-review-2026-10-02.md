### “待数据”与“验收通过”到底指什么

- **历史净收益归因**：当前卡片在归因缺失时仍为“当前权益 − 初始权益”。例如权益多了 110 USD、期间净入金 100 USD，排除资金投入后只有 10 USD。还要拆出交易盈亏、资金费、借贷利息和奖励，明确哪些属于策略交易收益。权益已经反映成交费用，不能为了归因再扣一次手续费。
- **本项目的实证缺口**：配置只有 `strategyStartAt=2026-09-30` 日期和 `strategyBaselineUsd=534.7`，没有精确的基线时刻；当前没有 attribution_ledger.json。原始成交已持续保存，仍不能替代完整现金流／历史资金费核对。
- **长期回测**：需要实现可复现的成交与成本模型，在未参与调参的数据上验证固定网格／动态轮换等方案。几天权益上涨、代码测试成功、纸上百分比并不能完成这项检验。当前纸上 open／closed 均为 0，尚无有效比较样本。
- **软件验收范围**：现有测试、正常只读观察、真实 dry-run、线上上传／读回及页面显示已验证；交易所网络异常主要在模拟 I/O 中验证，运行器取消／更深进程树、人工暂停原因与完整故障分支仍有边界。新增反例使“当前全部代码已验收”这一表述不再成立。

### N07 / P1：公共 markPrices 故障阻断已可判断的账户风险

证据：`scripts/observe.mjs:33–41`、`scripts/run_round.sh:18–22`。observe 在取到 automation／positions／account／collateral 后仍强制等待公共 markPrices；其失败会在构造、落盘观察之前退出。该接口在这里主要提供卡片价格，持仓估值已有持仓接口的 markPrice。

**复现**：有效账户数据已返回权益 100 USD，已知峰值 1000 USD，回撤为 90%（预算 80%）；仅 markPrices 返回 503，生产 observe 抛错且 observed.json 未更新。runner 直接 OBSERVE_FAILED，不执行 decide，因此无法根据已取得的权益落盘熔断。健康对照只恢复 marks 响应，生产 observe→decide 就落盘 paused 并派发 OLD 停止。这个缺口在 decide 的 tickers 降级之外。

建议：账户／持仓核心观察与展示行情分层；公共行情不可用时阻止新风险、标价格未知，允许账户熔断与可证明归属的 pending 核验继续。不能把未知持仓或损坏核心账本顺带当成正常。验收覆盖 markPrices 503／超时／坏 JSON，并对照健康路径。

### N08 / P1：账户身份只绑定 subaccountId，没有绑定 userId

证据：`scripts/decide.cjs:490–493`、`scripts/observe.mjs:125–127`、`scripts/act.mjs:180–204`。metadata 绑定配置与子账户编号，执行时 collateral 只匹配 `-3` 后缀；就算配置有 userId，也未比对会话中返回的实际 owner。

**复现**：配置指定 expected-owner，metadata 配置哈希合法，实际 collateral 唯一 key 为 different-owner-3；生产 act 仍确认 create 成功。这说明登录身份改变／账号切换时，子账户编号相同不足以锁定原授权目标；本轮没有切换真实账号。

建议：观察捕获、校验、固定 `userId + subaccountId` 的 accountKey，风险、pending、计划、执行结果、账本和缓存都带身份；执行前检查会话身份，不一致时终止交易动作并告警。不能把另一账户的网格作为本项目清理对象。验收覆盖空持仓下的身份判定、切账号、子账户同号及 pending 重试。

### N01 / P1：创建成功核验没有核对实际投入等完整参数

证据：`scripts/act.mjs:232–246, 302–307`。确认阶段只比较下界、levels 与 TP／SL／close；没有核对 allocationUsd、上界、方向、enabled，随后释放 create intent 并记 done=true。

**复现**：请求 500 USD，模拟接口回读 allocationUsd=100000，仍以创建成功结束、清空 pending；或请求上界 110、回读 150，结论也相同。极端数值用于证明客户端检查缺失，不代表交易所真实允许该金额或真实订单可落地。只要 API 静默归一、返回漂移或出现异常字段，前向预算就不能只以请求值为前提。

建议：数值规范化后逐一核对实际参数，按存储的真实金额／保护重新核验预算，订单恢复 kick 后再最终确认；不一致进入清理／自愈，完整核验成功后才释放意图。验收包括正常数值字符串、投入／上界／方向／enabled 漂移及清理失败。

### N02 / P1：执行前重读持仓，但未复评强平危险和字段完整性

证据：`scripts/act.mjs:190–204`。livePositions 仅判断是否为数组以及 symbol 是否属于配置；未验证数量／mark／liq，也未运行 cfg.liqDangerPct 规则。权益与配置预算合规不能替代持仓风险。

**复现**：旧网格仍在配置中，最新持仓 mark=100、liq=99，距离 1%（阈值 12%），create 被确认；换成同市场 netQuantity=null，同样确认。decide 两阶段会评估当时的持仓，但规划后数据再变化时此执行闸门没有覆盖。

建议：复用严格持仓 schema 和风险评估；最新数据未知或危险时否决 create，保留／追加退出意图并刷新状态。不能将合法“无强平价／liq=0”混为接口畸形。验收要覆盖从规划安全到执行危险、未知字段、良性零值及正常可创建对照。

### N03 / P2：动作日志可能把旧结果记到新失败轮次

证据：`scripts/run_events.cjs:15–18`、`scripts/run_round.sh:35–39`。act 在初始化、过期计划、配置哈希校验等阶段失败时不会覆盖 act_results.json；runner 的失败分支仍尝试把现有文件记入当前 run。

**复现**：旧文件包含 10-01 的 stop done=true；启动新 run，actions phase1 后以 act_failed 结束，日志却把旧 stop 带入新 runId。dashboard 的退出计数会计入它。它影响审计／次数，不证明本轮真的执行了停止。

建议：结果带 runId／planId／accountKey 并逐动作持久化；记录前核对匹配，否则写初始化失败或结果未知。拒绝过期结果，不仅按文件是否存在判断。验收覆盖 start 失败、首次网络调用失败、部分动作完成后崩溃和旧结果文件残留。

### N04 / P2：历史采集的完整性仍有三个可复现边界

证据：`scripts/history_core.cjs:17–18, 35–55`。

- 同页重复 ID 各带不同 fee：查重只对已存字典进行，整页提交前相互冲突未发现，后者覆盖前者，仍 incomplete=false。
- 未来 lastTo：有限数字通过结构检查，未查询就报告已追平。异常游标不能作为已覆盖历史的证明。
- 延迟入索引：第一次完整窗推进到 T 后，补到历史接口但 timestamp<T 的成交不会再查询到。该场景为模拟索引延迟，未断言真实 API 已丢成交。

建议：页内 ID 一致性检测、持久化 fill schema／游标与采样时刻校验；使用明确安全滞后或小范围重叠回扫并以 ID 去重，定期与交易所历史账单核对。扩展完整性语义，acquiredAt 不等于所有成交已独立对账。

### N05 / P2：归因导入会继承旧文件的其他账户记录

证据：`scripts/import_ledger.cjs:10–19`。校验 incoming.subaccountId，未校验已有 old.subaccountId；合并后将总文件标为 incoming 的账户。

**复现**：旧账户 2 的入金 100 USD 留在 ledger，导入账户 3 的空事件及完整覆盖声明后，文件被标为账户 3。权益增量 110 USD 被算成净收益 10 USD；跨账户的旧入金不应参与。

建议：旧／新账本、事件身份统一核对，不匹配拒绝导入；增量 coverage 不能简单覆盖掉之前区间，需核对连续性；导入过程加锁、唯一 tmp，并保存原始导出证明。修复后再接真实归因数据。当前真实 ledger 尚不存在，本轮没有污染实盘数据。

### N06 / P2：缓存分析会绕过已修改的流动性门槛

证据：`scripts/decide.cjs:281–285, 344–376`；`scripts/analyze.cjs:53–54`。缓存仅按 generatedAt 过期，minQvol24h 只在 analyze 中检查；configHash 绑定的是执行计划，不是缓存计算条件。

**复现**：minQvol24h 已改为 500 万，缓存候选及最新 ticker 成交额都是 100 万，缓存时间仍新鲜；真实 decide 仍输出 create。

建议：缓存带 configHash、样本时间、排除集合和 schema 版本；配置改变使相关缓存失效，创建前以最新行情复核最低成交额／标记价与区间。候选研究和替换规划避免以不同排除集合互相覆盖缓存。

### 进一步优化，暂不宣称可提升收益

- **验收层**：把上述反例转成目标行为回归，优先 N07／N08／N01／N02。当前测试仍保留较多逻辑复刻／源码金丝雀；配置确认、账号身份、观察降级、结果绑定和历史采集都应覆盖完整生产入口。
- **共享契约**：统一配置数值／范围、accountKey、position、automation、analysis、plan／result schema；不要每次在单个调用点补一个 if。现有 risk/pending 校验已有共享模块，其他边界仍各自处理。
- **可观测性**：为 run 写 start／heartbeat／end，监督进程异常退出；保留观察、决策、交易所请求、成交、资金费、现金流的关联 ID。确认内核锁与真实 ego 运行器取消／进程树语义，不能以 sleep 子进程测试替代全部运行器故障验证。
- **数据与研究**：优先按官方资金费／历史仓位接口补已有账本，校验符号和基线；纸上策略需资金权重、费用与资金费，closedTotal 百分比相加不是组合收益。随后做固定网格／动态轮换／冷却等相同风险与成本假设下的样本外对照。现阶段不改 80% 风险偏好，也不根据本轮审查扩规模。
- **规模与维护**：原始成交现用完整 JSON，每次保存和汇总遍历全历史；长期运行应考虑 SQLite／分段不可变归档和增量聚合。当前数据量较小，属维护优化，未当成现有资金风险。

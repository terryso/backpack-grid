## 2. 高优先级缺陷：建议先处理

### F01 / P1：分钟峰值探测可能覆盖熔断锁存

**证据：** `scripts/peak_probe.mjs:11–19, 26–37`。探测器只在开始时检查一次 `state/lock`，随后读取 risk、等待浏览器与接口，最后把最初读取的整个 risk 对象写回。它没有实际取得锁，也没有在提交时重新读取状态。

**已复现（R1）：** 探测器读取 `{peakEquity:600, paused:null}`；在请求等待期间，巡检写入权益 100、回撤熔断的 `paused` 对象；探测器随后获得权益 650，并以旧对象写入 `{peakEquity:650, paused:null}`。熔断锁存被清除。这是两个正常任务的允许交错，不涉及恶意进程。

**建议：** 两个任务共用风险状态写入事务。网络采样可在锁外进行；提交时取得同一把短事务锁，重新读取并严格校验最新 risk，合并峰值且保留最新 `paused`。避免各自使用相同 `.tmp` 文件并无锁覆盖。峰值探测器也应使用与 decide 相同的结构校验，不能将 `peakEquity:null` 通过数值转换修复成新基线。

**验收：** 人工控制“探测读旧值 → 巡检熔断 → 探测提交”的顺序，`paused` 必须保留；较低采样不能降低峰值；损坏状态必须保持原文并禁止自动重播种。

### F02 / P1：数据完整性校验仍有缺口

**证据：** `scripts/observe.mjs:46–64`，`scripts/act_core.cjs:43–64`。

三种场景已复现（R2、R2b、R2c）：

1. 网格账本有 `netPosition=1`、买入金额 100，但持仓数组没有对应条目。公共 `markPrices` 明明提供价格 100，代码仍用持仓条目得到的 `mark=0` 计算盈亏。观察校验通过，500 USD 配置被计算为 -20% 盈亏。公共价格只用于展示字段 `price`。
2. 找到了 snapshot 条目，但 `pnl` 缺失字段或为空对象时，全部默认 0，仍被接受为已知盈亏。
3. 持仓接口返回合法数组，但目标条目 `netQuantity:null`；`Number(null)===0`，平仓闸门通过，网格被删除、pending 被清除。

**建议：** 独立验证网格账本、仓位数量、价格和金额字段。非零账本库存必须有有效价格，并处理账本与持仓接口不一致的情况；可以使用公共标记价估值，但不能用它掩盖跨接口一致性问题。缺失字段不能自动成为零，只有接口契约明确的零值才可使用。平仓判断必须接受明确的数值零，拒绝 null、空字符串、布尔和非有限值。

**验收：** 上述三例都不能生成基于假盈亏的交易或清除未确认意图；真实零仓位与新网格合法零账本仍可正常处理。增加 observe 的完整执行测试，而不只检查源码字符串。

### F03 / P1：第二阶段补仓跳过存量网格风控

**证据：** `scripts/decide.cjs:185–186, 261–262`。`BG_PHASE=creates` 时，逐格止损、出界和强平距离循环直接跳过，仍可规划新网格。

**已复现（R4）：** 同一份观察数据中，存量网格 mark=100、liq=99，距离仅 1%。普通阶段生成 `stop OLD`；补仓阶段没有 stop，却生成 `create NEW`。

**建议：** 第二阶段使用最新快照再次执行所有存量风控。如果退出后有其他网格新出现危险，应先退出并取消本阶段创建。阶段标签只能控制是否规划新增仓位，不能屏蔽风控判断。配置预算也应在执行新建前以最新状态重新核验。

**验收：** 在第一阶段和第二阶段之间注入新的 SL、资金费调整后 SL、出界及 LIQ_DANGER，均不得继续创建；退出无异常时仍可按预算缩容补位。

### F04 / P1：PID 锁的失效锁接管仍非原子

**证据：** `scripts/run_round.sh:17–25`。已有目录锁、PID 缺失或已死亡时，接管者直接覆盖 `lock/pid`，没有再次进行原子竞争。

**已复现（R3）：** 两个进程都读取同一死亡 PID，随后都通过检查并覆盖 PID；两者均进入巡检主体。所有者检查减少了旧进程清理新锁的问题，但没有保证单一执行者。新建目录到写 PID 之间的无主窗口也有相同风险。

**建议：** 使用系统提供的互斥原语，或以原子方式竞争接管资格；记录所有者令牌和进程启动标识，释放时验证归属。将峰值探测器、主巡检和风险状态更新的锁协议统一。不要只增加超时或再加一次 `kill -0`。

**验收：** 活 owner、失效 owner、无主目录、两个并发接管者、owner 退出及 PID 复用场景，均最多一个巡检主体进入。测试整个锁协议，当前字符串金丝雀不足以证明互斥。

## 3. 运行恢复、统计与仪表盘

### F05 / P2：孤儿持仓仍在 observe 阶段阻断恢复

`decide.cjs:36–38` 已将孤儿持仓设计成“禁止新风险、允许 pending 核验”，但 `observe.mjs:192` 仍因 `positions.length > gridRows.length` 失败。R5 用“零网格、一个残仓”复现 `OBSERVE_FAILED`，外层 runner 因此无法进入 decide/act。

建议将明确数据畸形与合法但异常的账户状态分开。孤儿持仓应带显式告警、禁止新增风险；允许执行可证明归属的 pending 核验。归属未知的仓位需要明确人工处理，不能未经确认自动平掉。验收应执行 observe→decide→act 的完整恢复路径。

### F06 / P2：手续费历史采集存在确定性漏数

**证据：** `observe.mjs:125–149`。R6 模拟截至 10 月 2 日中午回补历史：9 月 30 日首个窗口返回不足 1000 笔，代码 `break`，却将 `lastTo` 推进到当前时间，后续 **36 小时未查询历史被标记为已完成**。新入选币种若最早窗口没有成交，也会受影响。

当一个窗口返回正好 1000 笔，代码也没有分页或缩小窗口，就推进到窗口末尾；R6b 证实只有一次请求。这不能证明已经收集完整窗口。

建议逐窗口完成采集，游标只推进至确认完整的窗口终点；满页时分页或切分时间区间，按 fill ID 去重。保存原始成交及完整性状态，而不仅是累加数字。用两个以上窗口、空窗口、1001+ 笔、边界成交和中断恢复测试对账。非 USDC 费用也需明确换算或标注未计入。

另一个执行影响是：费用历史查询在关键账户数据读取之后、`observed.at` 生成之前串行运行。它会增加风控等待，并让较早取得的账户数据看起来刚刚采集。建议将历史统计独立于交易巡检，记录 `acquiredAt`、采集跨度及统计时间。

### F07 / P2：仪表盘会将未知状态显示为正常

**证据：** `dashboard_data.cjs:8, 76–102`，`dashboard.html:104–118`。R7 同时提供 observation 的校验错误、损坏 risk 文件和 `pending_corrupt.json`，生成的快照仍是 `riskPaused:false`、空 pending，页面显示绿色“风控正常”。读取失败被默认成空对象，关键错误与禁止开仓标志没有进入展示模型。

建议输出 `dataValid`、`riskStateValid`、`pendingCorrupt`、`lastRoundStatus`、`snapshotAge`，对未知、过期、失败使用明确状态；保留合法零值与未知值的区别。显示一次 run 的汇总结果，不能只取 `act_results.results` 最后一条而遗漏前面的失败。

每格健康徽标使用账本 `pnlPct`，交易判断却加上资金费；应提供同口径的 effective PnL，避免距触发条件的展示偏差。

### F08 / P2：部署脚本与现行 Worker 凭证协议不一致

**静态确认：** Worker 要求 `DASH_WRITE_TOKEN`；`deploy_dashboard.sh:15, 35–36` 仍生成并设置 `DASH_TOKEN`，且 deploy/secret 命令没有指定 `--config cloudflare/wrangler.toml`。README 的重新部署命令会调用这个脚本。

建议统一环境变量、secret 名称和配置路径；给脚本增加 CLI stub 测试，断言目标 Worker、配置及 secret 参数正确。既有部署可能因已有 secret 正常工作，这不证明首次部署和凭证重建脚本正确。本次没有执行部署或读取密钥。

### F09 / P2：收益和运行统计需要明确计量口径

- `observe.mjs:164–171` 的累计盈亏是权益减固定基线。应记录净出入金，采用 `权益变化 - 净入金`，并另行归因借贷利息、活动奖励等。
- 当前资金费来自仍存在的仓位，无法替代策略全生命周期的资金费账本。
- `dashboard_data.cjs:52, 70–74` 用曲线行数表示巡检次数，用计划日志里的 stop 数表示换仓次数。dry-run、第二阶段及失败重试会影响这些计数。应按 run ID 和确认完成的执行事件统计。
- 历史最大回撤使用 15 分钟曲线，当前回撤使用分钟探测峰值，采样精度不同。应统一曲线数据源，或在界面注明采样范围，避免两种指标被当作同精度。
- 基于峰值的 80% 回撤限额与 `当前权益×80%` 配置预算不是同一公式。若峰值 1000、当前权益 800，则距 200 权益底线的空间为 600，而当前公式给出 640（均未扣缓冲）。应明确配置额度只是前向名义约束，或将预算改为与已接受的权益底线一致的剩余损失额度，并计入利润回吐、费用和滑点。此项是预算设计建议，不是本次实盘超亏结论。

### F10 / P3：点赞规则只在客户端执行，KV 增量也会丢更新

`worker.js:29–36` 无条件执行 read+1+write；R8 同一访客连续 POST 两次得到计数 2。前端置灰不构成服务端每日去重。并发更新也不能依靠 KV read-modify-write 保证原子性。

若保留“每 IP 每天一次”的规则，应服务端强制幂等；精确计数可使用 Durable Object 等具备串行一致性的机制，并给访客标记设置过期策略。仅作为展示点赞时也应明确统计是近似值。Cloudflare 官方文档说明 KV 不适合需要原子读改写的场景，见文末来源。

## 4. 策略与研究优化：先验证再改参数

下列项目需要数据与回测支撑，本次不把它们认定为已经有效的收益改进，也不改变正在运行的参数。

| 优化方向 | 当前不足 | 建议实验与验收 |
|---|---|---|
| 震荡质量 | chop 只度量路径/净位移，截尾后高值区分度有限；小时收盘路径不能表示所有可成交网格往返 | 增加区间往返、突破、停留、跳跃及波动稳定性；与现评分做样本外对照，含完整费用 |

| 实际缩容参数 | analyze 按配置 2500 检查每单金额；decide 可缩到 500/1950/2250，但沿用原 count | 按最终 value 重算格数、数量步长和最小名义额；报告真实价位对应的净格距；交易所 validate 作为最终检查 |
